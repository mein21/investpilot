# InvestPilot Local — исходное задание (source of truth)

> Этот файл содержит исходный промпт заказчика дословно. При каждой компакции
> контекста агент обязан перечитать этот файл целиком перед продолжением работы.

Ты работаешь как senior Python-разработчик и технический архитектор. Помоги реализовать локальное приложение InvestPilot Local для личного управления портфелем через официальный API T-Invest.

Ключевое ограничение:
готовое приложение НЕ должно использовать искусственный интеллект, LLM, машинное обучение, генерацию текста или внешние AI API во время работы. DeepSeek используется только для написания и проверки исходного кода. Все инвестиционные решения должны рассчитываться детерминированными правилами, формулами и настройками пользователя.

Цель приложения:
получать данные инвестиционного счета из T-Invest API, рассчитывать состояние портфеля, выявлять отклонения от целевой аллокации, формировать объяснимые рекомендации BUY, SELL, HOLD и REBALANCE, создавать черновики заявок и отправлять реальную заявку только после явного подтверждения пользователя.

Технологический стек:
- Python 3.12+
- FastAPI
- SQLAlchemy 2.x
- Pydantic v2
- SQLite для разработки
- PostgreSQL как подготовленный вариант production
- Jinja2 и HTMX для web-интерфейса
- Chart.js для графиков
- pytest
- httpx
- Docker Compose
- APScheduler или другой простой планировщик
- ruff
- mypy по возможности

Архитектурные требования:
1. Разделяй код на модули:
   - app/api
   - app/core
   - app/db
   - app/models
   - app/schemas
   - app/services
   - app/rules
   - app/risk
   - app/integrations/tinvest
   - app/notifications
   - tests
2. Интеграцию с T-Invest изолируй за интерфейсом TInvestClient.
3. Не смешивай HTTP-клиент, бизнес-правила и HTML-шаблоны.
4. Все денежные значения храни и рассчитывай через Decimal, а не float.
5. Временные значения храни с timezone.
6. Не делай предположений о названиях или сигнатурах API. Сначала сверяйся с официальной документацией T-Invest API.
7. Если документация недоступна, создай адаптер с TODO и mock-реализацией, но не выдумывай поля.
8. Все внешние ответы валидируй через Pydantic.
9. Добавляй retry только для безопасных GET-запросов. Отправку заявки нельзя автоматически повторять без idempotency-защиты.
10. Каждый запрос и ответ, связанный с заявкой, должен иметь audit log без секретных токенов.

Поддерживаемые режимы:
- OBSERVE: только чтение данных;
- RECOMMEND: расчет рекомендаций без отправки заявок;
- PAPER: симуляция заявок;
- CONFIRM: отправка только после подтверждения пользователя;
- AUTO: режим должен существовать как запрещенный feature flag и не включаться в первой версии.

Финансовые цели должны иметь:
- название;
- сумму;
- валюту;
- дату;
- регулярное пополнение;
- минимальный денежный резерв;
- допустимую просадку;
- профиль риска;
- целевую аллокацию.

Аллокация должна задаваться диапазонами:
- min_percent;
- target_percent;
- max_percent.

Правила покупок:
- не покупать при устаревших котировках;
- не покупать при недоступном инструменте;
- не нарушать денежный резерв;
- не превышать лимит эмитента;
- не превышать лимит класса активов;
- учитывать размер лота;
- учитывать комиссию;
- учитывать минимальный размер сделки;
- покупать в первую очередь недовзвешенные активы;
- не создавать рекомендацию, если ожидаемое исправление меньше минимального порога.

Правила продаж:
- продавать только при превышении max_percent;
- продавать при превышении лимита эмитента;
- продавать при исключении инструмента из списка;
- продавать при необходимости финансирования цели;
- учитывать стоп-правила пользователя;
- падение цены само по себе не должно быть причиной продажи;
- не создавать продажу, если она нарушит минимальный резерв или другой риск-лимит.

Рейтинг инструмента:
Используй прозрачный детерминированный score. Не называй его прогнозом цены.
Пример компонентов:
- allocation_need;
- risk_fit;
- liquidity;
- maturity_fit;
- income_fit;
- concentration_penalty;
- volatility_penalty.

Каждый компонент должен иметь описание, диапазон и тесты. Итоговый score должен быть воспроизводимым.

Рекомендация должна содержать:
- action: BUY, SELL, HOLD, REBALANCE;
- figi или официальный идентификатор инструмента;
- ticker;
- количество лотов;
- ориентировочную сумму;
- тип заявки;
- причину;
- сработавшие правила;
- заблокировавшие правила;
- ожидаемую долю после сделки;
- риски;
- время расчета;
- актуальность данных;
- статус: NEW, APPROVED, REJECTED, SENT, EXECUTED, FAILED, EXPIRED.

Торговые ограничения:
- реальная торговля отключена по умолчанию;
- Sandbox включен по умолчанию;
- реальная заявка требует явного подтверждения;
- перед отправкой повторно проверить баланс, цену, торговый статус и риск-лимиты;
- добавить max_order_amount;
- добавить max_daily_order_amount;
- добавить max_daily_order_count;
- добавить emergency_stop;
- не отправлять заявку при устаревших данных;
- не отправлять дублирующую заявку;
- не скрывать частичное исполнение.
